El modelo funciona en el script. Para que sirva hay que guardarlo de forma que otro proceso lo cargue con su tokenizador, predecir rápido cuando llegan muchas reseñas a la vez y tratar los textos que no se parecen a los de entrenamiento. Y antes de desplegar nada, conviene hacerse una pregunta que en 2019 no existía: **¿haría falta este modelo, o bastaría con preguntarle a un LLM?**

## Guardar modelo y tokenizador juntos

```python
model.save_pretrained("modelo-estrellas")       # config.json + model.safetensors
tokenizer.save_pretrained("modelo-estrellas")   # vocabulario y configuración del tokenizador
```

La carpeta lleva todo lo necesario: la arquitectura (`config.json`, con los nombres de las clases que pusimos en `id2label`), los pesos en *safetensors* (un formato que, a diferencia de pickle, no puede ejecutar código al cargarse) y el tokenizador. La nuestra ocupa 440 MB, casi todo pesos: 110 millones de parámetros a 4 bytes.

Para usarlo, `pipeline` junta tokenizador, modelo y softmax:

```python
from transformers import pipeline

clasificador = pipeline("text-classification", model="modelo-estrellas", device="cpu")
clasificador("Se rompió a la semana y el vendedor no responde. No lo recomiendo.")
```

Con cuatro reseñas escritas para el tutorial:

| Reseña | Predicción | Probabilidad |

| «Llegó en dos días y funciona perfectamente. Muy contento con la compra.» | 5★ | 0,86 |
| «Cumple, sin más. Por este precio no se puede pedir mucho.» | 4★ | 0,58 |
| «Se rompió a la semana y el vendedor no responde. No lo recomiendo.» | 1★ | 0,95 |

Razonables, y con la confianza donde toca: muy alta en los extremos, más baja en el «cumple, sin más», que igual podría ser un 3.

## Lotes y longitud

En producción las reseñas llegan de una en una (una API) o a miles (un proceso nocturno). Procesarlas en lotes aprovecha mucho mejor el hardware, pero cada lote se rellena hasta su texto más largo. Si se mezclan al azar reseñas de 10 y de 120 tokens, la mayor parte del cálculo se gasta en relleno. El truco: **ordenar por longitud** antes de hacer los lotes.

    import numpy as np

    def padding_share(lengths, batch_size):
        """Proporción de posiciones de relleno si se hacen lotes en el orden dado."""
        total = relleno = 0
        for start in range(0, len(lengths), batch_size):
            lote = lengths[start:start + batch_size]
            ancho = max(lote)                          # se rellena hasta el más largo del lote
            total += ancho * len(lote)
            relleno += ancho * len(lote) - sum(lote)
        return relleno / total

    rng = np.random.default_rng(0)
    longitudes = list(np.clip(rng.lognormal(3.4, 0.7, 2000).astype(int), 3, 128))

En la CPU del portátil, BETO tarda unos **31 ms por reseña** si se procesan de una en una y **24 ms** en lotes de 32, sin ordenar. Los lotes del script van sin ordenar, así que una parte del cálculo se va en relleno; ordenándolos, como en el ejercicio, el ahorro sería mayor. En una API que recibe una reseña cada vez, lo que manda es la latencia de una sola.
