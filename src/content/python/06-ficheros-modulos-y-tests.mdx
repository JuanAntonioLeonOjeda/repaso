Un análisis no vive solo en tu cabeza ni en una celda de Jupyter: lee ficheros, escribe resultados, se reparte en módulos que otros importan, depende de librerías con versiones concretas y, si es serio, tiene tests que avisan cuando algo se rompe. ## Leer y escribir ficheros

```python
with open("datos.txt", encoding="utf-8") as f:   # 'r' (leer) es el modo por defecto
    contenido = f.read()                          # todo el fichero en un str

with open("datos.txt", encoding="utf-8") as f:
    for linea in f:                               # línea a línea, sin cargarlo entero
        print(linea.rstrip("\n"))

with open("salida.txt", "w", encoding="utf-8") as f:   # 'w' sobrescribe, 'a' añade al final
    f.write("hola\n")
```

- `with` **cierra el fichero** aunque salte una excepción. Sin él, un fichero abierto puede quedarse sin escribir del todo.
- Pon siempre `encoding="utf-8"`: el valor por defecto depende del sistema operativo y es la causa clásica de las «Ã±» en lugar de «ñ».
- Modos: `"r"`, `"w"`, `"a"`, `"x"` (crear, falla si existe) y `"b"` para binario (`"rb"` para imágenes).
- Para rutas, `pathlib.Path`: `Path("res") / "datos.csv"`, `.exists()`, `.glob("*.csv")`, `.read_text()`.

## Módulos, paquetes y entornos

- Un **módulo** es un fichero `.py`; un **paquete**, una carpeta de módulos (con `__init__.py`). `import utils`, `from utils import limpiar`, `import numpy as np`.
- Al importar un módulo, **se ejecuta todo su código de nivel superior**. Por eso el código que solo debe correr al lanzar el fichero como script va dentro de `if __name__ == "__main__":`.
- Cada módulo tiene su propio **espacio de nombres**: `math.sqrt` y `numpy.sqrt` no chocan. Evita `from x import *`, que mezcla los nombres de todos.

### pip y entornos virtuales

`pip install pandas` instala en el Python activo. Si todos tus proyectos comparten un Python, tarde o temprano uno necesita `pandas 2` y otro `pandas 3`. La solución es un **entorno virtual por proyecto**:

```bash
python -m venv .venv            # crear
source .venv/bin/activate       # activar (Windows: .venv\Scripts\activate)
pip install pandas==3.0.2       # instalar en ESE entorno
pip freeze > requirements.txt   # apuntar las versiones exactas
```

<Callout kind="real" title="Lo que se usa hoy">
El curso usa `pip`, `pipenv` (de ahí el `Pipfile` del repositorio) y conda. En equipos actuales se ha impuesto **uv** (`uv venv`, `uv add pandas`, `uv run script.py`), que hace lo mismo muchísimo más rápido y genera un *lockfile* con las versiones exactas, para que tu compañero y el servidor instalen lo mismo que tú. Lo importante no es la herramienta: es **fijar versiones** y no instalar nada en el Python del sistema.
</Callout>

## Tests

Un test es código que comprueba que otro código hace lo que debe. Con **pytest**, cualquier función que empiece por `test_` en un fichero `test_*.py` es un test, y se comprueba con un simple `assert`:

```python
# test_limpieza.py
from limpieza import eliminar_duplicados

def test_conserva_el_orden():
    assert eliminar_duplicados([3, 1, 3, 2]) == [3, 1, 2]

def test_lista_vacia():
    assert eliminar_duplicados([]) == []
```

Se ejecutan con `pytest` en la terminal. La pirámide de tests dice que conviene tener **muchos tests unitarios** (rápidos, de una función), menos de integración y pocos de extremo a extremo. Y **TDD** (*test-driven development*) propone escribir el test antes que el código: test que falla → código mínimo para que pase → mejorar el código con los tests en verde.

Un buen test no es el que pasa: es el que **fallaría si el código estuviera mal**. Ponlo a prueba:

## Para llevar

- `with open(..., encoding="utf-8")` siempre; `csv` y `json` para formatos estándar; `pathlib` para rutas.
- `if __name__ == "__main__":` separa lo que hace el fichero como script de lo que ofrece como módulo.
- Un entorno virtual por proyecto y versiones fijadas (`requirements.txt` o un *lockfile*).
- Nombres claros, funciones pequeñas, comentarios del porqué y docstrings.
