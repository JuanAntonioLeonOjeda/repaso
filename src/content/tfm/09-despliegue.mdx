Un modelo en un notebook no le sirve a nadie. La última parte del TFM lo convierte en un **servicio**: una API con FastAPI, empaquetada en Docker, con tests. Es la fase de despliegue de CRISP-DM, y la que más se pregunta en una entrevista.

## De `infer.py` a una API

`infer.py` predice sobre un DICOM o un paciente desde la línea de comandos, con el **mismo preprocesado que en entrenamiento** (inversión MONOCHROME1, 224×224, CLAHE, normalización ImageNet). La API (`api/`) reutiliza ese código:

- `GET /health`: para que Docker (o un orquestador) sepa si el servicio está vivo.
- `POST /predict` (multipart): el DICOM y los datos clínicos validados por FastAPI (`age` entre 0 y 120, `gender` `female`/`male`, `bmi` entre 0 y 80) y, opcionalmente, `heatmap=true` para recibir el Grad-CAM en PNG codificado en base64.
- Si el DICOM no se puede procesar, responde **422** con el motivo, en vez de un error 500.
- El modelo se carga **una vez** al arrancar (`lifespan`), no en cada petición.

```bash
curl -X POST localhost:8000/predict -F dicom=@radiografia.dcm \
     -F age=65 -F gender=female -F bmi=24.5 -F heatmap=true
```

<Callout kind="warn" title="El detalle que rompe más modelos en producción">
Las covariables se normalizan con la media y desviación de **entrenamiento**. Por eso el TFM guarda `best_phased_full_covars_covariates.json` junto al checkpoint y la API lo lee: si en producción normalizases con los datos que llegan, cada paciente "cambiaría" según quién más hubiera llegado ese día. Es el mismo principio que el `fit` en train y `transform` en test de Supervisado, llevado a producción.
</Callout>

## Docker

El `Dockerfile` del TFM sigue buenas prácticas que conviene saber defender:

- Imagen base `python:3.13-slim` y solo las librerías de sistema que necesita OpenCV.
- Dependencias de la API (`requirements-api.txt`) separadas de las de entrenamiento: la imagen no lleva lo que no usa.
- **El modelo no va dentro de la imagen**: se monta como volumen en `/models` (`MODEL_DIR`). Así se actualiza el modelo sin reconstruir, y la imagen no contiene artefactos derivados de datos de pacientes.
- Usuario sin privilegios (`appuser`) y `HEALTHCHECK` contra `/health`.

## Lo que faltaría para uso clínico real

<Callout kind="real">
- **Validación externa**: probar con radiografías de otros hospitales y equipos. Es el paso que más modelos médicos no superan.
- **Calibración**: que una probabilidad de 0,7 signifique un 70% de verdad (temperature scaling).
- **Umbral de decisión**: elegido según el coste de cada error (en cribado, favorecer la sensibilidad en osteoporosis).
- **Monitorización**: distribución de las entradas y de las predicciones en producción, para detectar deriva.
- **Regulación**: un software que apoya el diagnóstico es un producto sanitario (MDR en la UE) y un sistema de alto riesgo según el Reglamento de IA europeo.
</Callout>

## Para llevar

- `infer.py` y la API comparten el preprocesado del entrenamiento: una sola fuente de verdad.
- FastAPI valida las entradas y responde 422 si el DICOM no se puede procesar; el modelo se carga una vez.
- Estadísticas de covariables guardadas con el checkpoint; modelo montado como volumen.
- Para la clínica faltarían validación externa, calibración, monitorización y el marco regulatorio.
