La API funciona en tu portátil con `fastapi dev`. En producción hay que pensar en otras cosas: cuántos procesos, cómo se empaqueta, quién puede llamarla desde un navegador, cómo se sigue una petición en los logs, cómo cambiar la API sin romper a sus clientes. Esta última lección es la lista de lo que separa una demo de un servicio.

## Servidor y procesos

FastAPI es la aplicación; quien escucha en el puerto es un **servidor ASGI**, normalmente **Uvicorn**.

```bash
fastapi run app/main.py --port 8000 --workers 4
# equivalente:
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
```

Cada *worker* es un **proceso** con su propio Python, su event loop y su copia del modelo en memoria. Es la forma de usar varios núcleos (el GIL impide hacerlo con hilos, lección 10). Una regla de partida es un worker por núcleo; si el modelo es grande, la memoria pone el límite antes.

En Kubernetes o similares, lo habitual es **un proceso por contenedor** y escalar con réplicas: el orquestador reparte el tráfico y reinicia lo que falla.

## Empaquetar con Docker

```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # incluye "fastapi[standard]", que trae el comando fastapi
COPY app ./app
COPY models ./models
RUN useradd --create-home api
USER api                                              # nunca como root
EXPOSE 8000
CMD ["fastapi", "run", "app/main.py", "--port", "8000"]    # un proceso: se escala con réplicas
```

Y dos endpoints para el orquestador: **liveness** (`/health`: el proceso responde) y **readiness** (`/ready`: el modelo está cargado y la base de datos responde). Si la readiness falla, el balanceador deja de mandarle tráfico sin matar el contenedor.

## CORS: quién puede llamarte desde un navegador

Si el frontend vive en `https://app.example.com` y la API en `https://api.example.com`, el navegador **no deja** que el JavaScript de la web lea las respuestas de la API, salvo que la API diga explícitamente que ese origen está permitido. Eso es CORS, y en FastAPI es un middleware:

## Seguir una petición en los logs

Con varios procesos y réplicas, los logs de una petición se mezclan con los de cientos. La solución estándar es un **id de petición**: se toma de la cabecera `X-Request-ID` si viene (el balanceador o el frontend la ponen) o se genera, se escribe en cada línea de log y se devuelve en la respuesta. Cuando un usuario reporta un error, te da ese id y encuentras todo.

  solution={`
    import time
    import uuid

    import httpx
    from fastapi import FastAPI, Request

    app = FastAPI()

    @app.middleware("http")
    async def request_context(request: Request, call_next):
        request_id = request.headers.get("X-Request-ID") or str(uuid.uuid4())
        request.state.request_id = request_id
        start = time.perf_counter()
        response = await call_next(request)
        elapsed_ms = (time.perf_counter() - start) * 1000
        response.headers["X-Request-ID"] = request_id
        response.headers["X-Process-Time-Ms"] = f"{elapsed_ms:.1f}"
        return response

    def predict(request: Request):

        print(f"[{request.state.request_id}] prediciendo")

## Cambiar la API sin romper a nadie

Una vez publicada, otros dependen de la forma de tus respuestas. Añadir un campo opcional es seguro; **renombrar o quitar** un campo, cambiar su tipo o hacer obligatorio un parámetro rompe a los clientes. Para eso, **versiones**: los cambios incompatibles van a `/v2` mientras `/v1` sigue funcionando un tiempo.

<Callout kind="real" title="La lista antes de publicar">
- **HTTPS** siempre, terminado normalmente en el balanceador o un proxy (nginx, Traefik). Detrás de un proxy, Uvicorn solo se fía de sus cabeceras `X-Forwarded-*` si la IP del proxy está en `--forwarded-allow-ips` (por defecto, solo `127.0.0.1`); si no, verás la IP del proxy en vez de la del cliente y `http` en vez de `https`.
- El middleware del ejercicio (`@app.middleware("http")`) es cómodo pero tiene pegas conocidas (más coste por petición, y las variables de contexto no llegan al endpoint): en producción se usa un middleware ASGI puro o una librería como `asgi-correlation-id`. Y el id que manda el cliente se valida (longitud y caracteres) antes de escribirlo en los logs.
- **Logs estructurados** (JSON) con el id de petición; **métricas** (latencia, tasa de 5xx, por endpoint) con Prometheus u OpenTelemetry; **trazas** si hay varios servicios.
- **Límites**: tamaño máximo del cuerpo, `max_length` en listas y textos, *rate limiting* por cliente (normalmente en el API gateway o el proxy; dentro de la app, con `slowapi`), timeouts en todo lo que llames.
- `/docs` desactivado o protegido en producción si la API no es pública (`FastAPI(docs_url=None, redoc_url=None)`).
- Secretos desde el entorno, dependencias fijadas (`uv.lock`, `requirements.txt` con versiones), imagen sin root y escaneada.
- Los tests y un *linter* (`ruff`) en CI, y despliegue automático tras pasar.
</Callout>

## Para llevar

- Uvicorn sirve la app; varios workers (procesos) o réplicas para usar varios núcleos.
- Docker con dependencias en una capa propia, usuario sin privilegios y endpoints de liveness y readiness.
- CORS decide qué webs pueden leer tus respuestas desde un navegador; no protege la API.
- Un id por petición en las cabeceras y en los logs.
- Los cambios incompatibles, a una versión nueva (`/v2`), manteniendo la anterior un tiempo.
