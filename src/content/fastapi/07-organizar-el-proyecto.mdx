Un `main.py` con cuarenta endpoints, los modelos de la base de datos, los esquemas y la configuración es manejable una semana. Después, cada cambio es buscar en un fichero de mil líneas. Esta lección es la estructura que vas a encontrarte (y montar) en un proyecto real: **routers** para dividir la API, **configuración** desde variables de entorno y **lifespan** para lo que se prepara una vez al arrancar, como cargar el modelo.

## Una estructura que escala

```
wine-api/
├── app/
│   ├── main.py            # crea la app, incluye los routers, lifespan
│   ├── config.py          # Settings: lo que cambia entre entornos
│   ├── db.py              # engine, SessionLocal, get_session
│   ├── deps.py            # dependencias compartidas (SessionDep, CurrentUser…)
│   ├── models.py          # tablas de SQLAlchemy
│   ├── schemas.py         # modelos de Pydantic (entrada/salida)
│   ├── ml.py              # cargar el modelo y predecir
│   └── routers/
│       ├── models.py      # /models
│       ├── predictions.py # /predictions
│       └── users.py       # /users, /auth
├── tests/
├── pyproject.toml
└── Dockerfile
```

No es la única forma (en proyectos grandes se agrupa por dominio: `predictions/router.py`, `predictions/schemas.py`…), pero la idea es la misma: **cada fichero, una responsabilidad**.

## APIRouter

Un `APIRouter` es una mini-app: se le añaden endpoints igual que a `app` y luego se incluye en la app con un prefijo. Todo lo que tengan en común los endpoints del grupo (prefijo, etiquetas para `/docs`, dependencias) se declara una vez en el router.

```python
# app/routers/models.py
router = APIRouter(prefix="/models", tags=["models"])

@router.get("")            # → GET /models
def list_models(): ...

@router.get("/{model_id}") # → GET /models/{model_id}
def get_model(model_id: int): ...

# app/main.py
app.include_router(models.router)
```

## Configuración desde el entorno

La URL de la base de datos, la clave para firmar tokens o la ruta del modelo **cambian entre tu portátil, los tests y producción**, y algunas son secretas. No van en el código: van en **variables de entorno**, y la app las lee en un objeto `Settings`.

En un proyecto real se usa `pydantic-settings`, que hace todo esto solo (lee las variables, valida los tipos, admite un fichero `.env`):

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str = "sqlite:///wine.db"   # lee DATABASE_URL si existe
    secret_key: str                            # obligatoria: sin ella, la app no arranca
    model_path: str = "models/wine-v1.joblib"
```

Aquí no tenemos `pydantic-settings`, pero la idea se puede hacer con Pydantic y `os.environ`. Lo importante es el patrón: **una función cacheada** que construye la configuración una vez, usada como dependencia (y por tanto sustituible en los tests).

## Lifespan: lo que se hace una vez

Cargar un modelo puede tardar segundos y ocupar cientos de MB: no se hace en cada petición. Se hace **una vez al arrancar**, en el `lifespan`, una función que se ejecuta hasta el `yield` al arrancar y después del `yield` al apagar:

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = get_settings()
    app.state.model = load_model(settings.model_path)   # al arrancar
    yield
    app.state.model = None                              # al apagar (cerrar conexiones…)

app = FastAPI(lifespan=lifespan)

@app.post("/predictions")
def predict(sample: WineSample, request: Request):
    return {"quality": request.app.state.model.predict(sample)}
```

<Callout kind="note" title="El lifespan en los tests">
`ASGITransport` no ejecuta el lifespan por sí solo. Aquí lo arrancamos a mano con `async with app.router.lifespan_context(app):`. En tu máquina, `TestClient` lo ejecuta si lo usas como gestor de contexto: `with TestClient(app) as client:`. Sin el `with`, el modelo no se carga y el test falla de forma confusa.
</Callout>

<Callout kind="real" title="Cómo se hace en el trabajo">
- `@app.on_event("startup")` y `"shutdown"` están obsoletos: verás código antiguo con ellos, pero lo nuevo usa `lifespan`.
- Los secretos nunca en el repositorio: variables de entorno inyectadas por la plataforma (Kubernetes *secrets*, AWS Secrets Manager, las variables de tu PaaS). El `.env` es solo para desarrollo y va en `.gitignore`.
- La configuración se valida **al arrancar**: si falta `SECRET_KEY`, mejor que la app no arranque a que falle a las tres de la mañana en la primera petición que la usa.
- Un `app.state.model` funciona, pero muchos equipos prefieren una dependencia `get_model` que lo lea de ahí: el endpoint queda más claro y el test puede sustituirlo con `dependency_overrides`.
</Callout>

## Para llevar

- Estructura por responsabilidades: routers, esquemas, modelos de BD, dependencias, configuración.
- `APIRouter(prefix=..., tags=..., dependencies=[...])` agrupa endpoints; `app.include_router` los añade.
- Configuración desde variables de entorno, en un `Settings` validado y cacheado, usado como dependencia.
- `lifespan` prepara lo caro una vez al arrancar (el modelo) y lo libera al apagar.
- En tests, el lifespan hay que arrancarlo: `with TestClient(app)` o `lifespan_context`.
