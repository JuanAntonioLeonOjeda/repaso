Una API se juzga tanto por cómo falla como por cómo funciona. Si pides un modelo que no existe y te llega un `500 Internal Server Error`, no sabes si el fallo es tuyo o del servidor; si te llega un `404` con `"Modelo 99 no encontrado"`, sí. Esta lección va de devolver **el código correcto con un mensaje útil**, y de entender en qué punto del camino de una petición sale cada error.

## Los códigos que vas a usar

| Código | Nombre | Cuándo |
|---|---|---|
| 200 | OK | lectura o actualización correcta |
| 201 | Created | se ha creado algo (`POST`) |
| 204 | No Content | correcto y sin nada que devolver (`DELETE`) |
| 400 | Bad Request | petición mal formada, o una regla de negocio que no encaja en otro código (FastAPI usa 422 para el esquema) |
| 401 | Unauthorized | no sé quién eres: falta el token o no es válido |
| 403 | Forbidden | sé quién eres, pero no puedes hacer esto |
| 404 | Not Found | el recurso no existe |
| 409 | Conflict | choca con el estado actual (ese email ya existe) |
| 422 | Unprocessable Content | los datos no cumplen el esquema (lo pone FastAPI) |
| 500 | Internal Server Error | un bug tuyo que nadie capturó |
| 503 | Service Unavailable | ahora no puedo (el modelo aún se está cargando) |

## HTTPException

Para cortar la petición con un código y un mensaje, se **lanza** `HTTPException`. Al lanzarla (no devolverla) da igual lo profundo que estés: FastAPI la captura y la convierte en la respuesta.

```python
from fastapi import HTTPException, status

@app.get("/models/{model_id}")
def get_model(model_id: int):
    if model_id not in MODELS:
        raise HTTPException(status.HTTP_404_NOT_FOUND, detail=f"Modelo {model_id} no encontrado")
    return MODELS[model_id]
```

Las constantes de `status` (`status.HTTP_404_NOT_FOUND`) se leen mejor que el número suelto y el editor las autocompleta.

## Tus propias excepciones

Lanzar `HTTPException` desde la lógica de negocio la ata a HTTP. Lo más limpio es que la lógica lance **excepciones propias** (`ModelNotReady`, `QuotaExceeded`) y registrar un **manejador** que las traduce a una respuesta. Así todos los errores tienen el mismo formato, se lancen donde se lancen.

```python
class ModelNotReady(Exception):
    def __init__(self, name: str):
        self.name = name

@app.exception_handler(ModelNotReady)
async def model_not_ready_handler(request: Request, exc: ModelNotReady):
    return JSONResponse(status_code=503, content={...}, headers={"Retry-After": "30"})
```

## Y el 500

Una excepción que nadie captura (un `KeyError`, una división entre cero) acaba en un **500** con el texto `Internal Server Error`, sin detalles. Eso es lo correcto: el traceback va a **tus logs**, no al cliente, porque puede revelar rutas, consultas o datos.

<Callout kind="note" title="En los tests, el 500 se convierte en excepción">
Ni `TestClient` ni `ASGITransport` te devuelven un 500 por defecto: **relanzan la excepción** en el test, para que veas el traceback. Si quieres comprobar la respuesta que vería el cliente, usa `ASGITransport(app=app, raise_app_exceptions=False)` o `TestClient(app, raise_server_exceptions=False)`.
</Callout>

<Callout kind="real" title="Cómo se hace en el trabajo">
- Un **formato de error único** en toda la API (`{"error": {"code", "message"}}`, o el estándar RFC 9457 *Problem Details*, con `type`, `title`, `status` y `detail`). El frontend lo trata en un solo sitio.
- Los `code` legibles por máquina (`model_not_ready`) importan más que el mensaje: el mensaje cambia o se traduce; el código no.
- Los 500 se monitorizan (Sentry, alertas en los logs). Un 4xx es normal; una subida de 500 es un incidente.
- No uses 200 con `{"ok": false}`: proxies, reintentos y métricas confían en el código de estado.
</Callout>

## Para llevar

- Cada situación tiene su código: 201 al crear, 204 al borrar, 401 sin identidad, 403 sin permiso, 404 si no existe, 409 si choca, 422 si el esquema falla.
- `raise HTTPException(status, detail=...)` corta la petición desde cualquier sitio.
- Orden: rutas → dependencias → validación → endpoint → `response_model`. La primera que falla decide (si una dependencia tiene sus propios parámetros inválidos, su error se junta con los de validación en un 422).
- Excepciones propias + `@app.exception_handler` dan un formato de error coherente.
- Un 500 es un bug: detalles a los logs, nunca al cliente.
