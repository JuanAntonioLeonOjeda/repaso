Para pedir una predicción, el cliente manda un JSON con las características del vino. ¿Y si falta un campo, llega un texto donde va un número o el alcohol es −3? Comprobarlo a mano en cada endpoint es largo y se olvida. En FastAPI describes la forma de los datos **una vez**, con una clase de **Pydantic**, y FastAPI la usa para validar la entrada, filtrar la salida y documentar ambas.

## Un modelo para el cuerpo

```python
from pydantic import BaseModel, Field

class WineSample(BaseModel):
    alcohol: float = Field(ge=8, le=15, description="% vol")
    volatile_acidity: float = Field(ge=0, le=2)
    sulphates: float = Field(ge=0, le=2)
    citric_acid: float = Field(ge=0, le=1, default=0)

@app.post("/predictions")
def predict(sample: WineSample):
    return {"quality": model.predict(sample)}
```

Un parámetro cuyo tipo es un `BaseModel` se lee del **cuerpo** de la petición. Dentro de la función, `sample` ya es un objeto validado: `sample.alcohol` es un `float` entre 8 y 15, garantizado.

Si algo no cuadra, FastAPI responde **422** con una lista de errores que dice qué falló y dónde:

```json
{"detail": [{"type": "greater_than_equal", "loc": ["body", "alcohol"],
             "msg": "Input should be greater than or equal to 8", "input": -3, "ctx": {"ge": 8.0}}]}
```

`loc` es la ruta hasta el dato: `body` (podría ser `query`, `path` o `header`) y el campo. Ese formato es estable: el frontend lo usa para pintar el error junto al campo del formulario.

## Lo que entra no es lo que sale

Un error que se ve en muchos proyectos: el endpoint que crea un usuario devuelve el objeto tal cual... con el hash de la contraseña dentro. La solución es tener **modelos distintos para entrada y salida** y decirle a FastAPI cuál es la salida con `response_model`. FastAPI **filtra** lo que devuelves y se queda solo con los campos de ese modelo.

```python
class UserCreate(BaseModel):     # lo que manda el cliente
    email: str
    password: str = Field(min_length=8)

class UserRead(BaseModel):       # lo que ve el cliente
    id: int
    email: str

@app.post("/users", response_model=UserRead, status_code=201)
def create_user(user: UserCreate):
    return {"id": 1, "email": user.email, "password_hash": hash_password(user.password)}
    # ↑ password_hash no sale: no está en UserRead (hash_password, en la lección 8)
```

<Callout kind="idea" title="También vale la anotación de retorno">
En vez de `response_model=UserRead` puedes escribir `def create_user(user: UserCreate) -> UserRead:`. FastAPI lo trata igual. La diferencia es que entonces la función debe devolver de verdad un `UserRead` (el comprobador de tipos te avisará si devuelves un dict con más campos), mientras que con `response_model` puedes devolver cualquier cosa y FastAPI filtra.
</Callout>

<Callout kind="real" title="Cómo se hace en el trabajo">
- Lo habitual es una familia de esquemas por recurso: `ModelCreate`, `ModelRead`, `ModelUpdate` (y a veces `ModelInDB`). Parece repetición, pero cada uno tiene un trabajo distinto, y mezclarlos es como acaban filtrándose hashes o campos internos.
- `ConfigDict(extra="forbid")` hace que un campo desconocido dé 422 en vez de ignorarse en silencio: útil para pillar erratas del cliente (`alchohol`).
- Para emails de verdad está `EmailStr` (necesita el paquete `email-validator`), y para validaciones que dependen de varios campos, `@model_validator`.
</Callout>

## Para llevar

- Un parámetro anotado con un `BaseModel` es el cuerpo de la petición; FastAPI lo valida y responde 422 con `loc`, `msg` y `type` si no cuadra.
- `Field(ge=..., le=..., min_length=...)` pone las restricciones; Pydantic convierte lo que tiene conversión obvia.
- `response_model` (o la anotación de retorno) filtra la salida: modelos distintos para entrar y salir.
- PATCH: campos opcionales y `model_dump(exclude_unset=True)`.
- Crear responde 201.
