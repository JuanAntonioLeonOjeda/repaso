Una API sin tests se rompe en silencio: cambias el esquema de un endpoint y otro deja de validar, refactorizas la autenticación y un endpoint queda abierto. FastAPI pone los tests fáciles (cliente en memoria, dependencias sustituibles), así que no hay excusa. Esta lección es cómo se escriben **en tu máquina con pytest** y, sobre todo, cómo saber si **tus tests sirven para algo**.

## En tu máquina: pytest y TestClient

```python
# tests/conftest.py
import pytest
from fastapi.testclient import TestClient
from app.main import app

@pytest.fixture
def client():
    with TestClient(app) as c:      # el with ejecuta el lifespan
        yield c
    app.dependency_overrides.clear()

# tests/test_models.py
def test_get_missing_model_returns_404(client):
    r = client.get("/models/999")
    assert r.status_code == 404
    assert r.json() == {"detail": "Modelo 999 no encontrado"}

@pytest.mark.parametrize("limit", [0, 51, -1])
def test_limit_out_of_range_is_rejected(client, limit):
    assert client.get("/models", params={"limit": limit}).status_code == 422
```

```bash
pytest -q                 # descubre tests/test_*.py y ejecuta cada función test_*
pytest -k 404 -x          # solo los que contienen "404", parando en el primer fallo
```

pytest **descubre** las funciones que empiezan por `test_`, les pasa las *fixtures* que piden por nombre (`client`) y da por bueno el test si ningún `assert` falla. Aquí haremos lo mismo con un pequeño ejecutor y `httpx.AsyncClient` (con `await`), porque en el navegador no hay `TestClient`.

## ¿Tus tests detectan algo?

Un test que siempre pasa no sirve. La forma honesta de medirlo es **meter bugs a propósito** y ver si algún test falla: se llama *mutation testing* (en Python, `mutmut` lo automatiza). La app del ejercicio tiene un interruptor `bugs` para eso.

## Cada test, su propia base de datos

El error más común en los tests de una API: compartir estado. Un test crea un usuario, el siguiente asume que la tabla está vacía, y el resultado depende del orden en que se ejecuten. La solución es que **cada test arranque con una base de datos limpia**, y se consigue sustituyendo la dependencia de la sesión.

<Callout kind="real" title="Cómo se hace en el trabajo">
- La pirámide en una API: muchos tests de **endpoint** con `TestClient` (rápidos, prueban validación, códigos, permisos), algunos de **integración** contra un PostgreSQL de verdad (Docker, `testcontainers`), y pocos de extremo a extremo.
- Lo que más merece un test: los **permisos** (que un usuario no pueda ver lo de otro), los casos de error (404, 409, 422) y el contrato de la respuesta. Los caminos felices se prueban solos al usar la API; los errores, no.
- Los tests corren en **CI** en cada pull request (GitHub Actions), con la cobertura (`pytest --cov`) como pista, no como objetivo: una cobertura del 100 % con asserts flojos no detecta nada, como acabas de ver.
- Para código `async` (un cliente asíncrono, un motor de BD asíncrono) se usa el plugin de pytest que trae `anyio` (`@pytest.mark.anyio`) o `pytest-asyncio`, con `httpx.AsyncClient`, como aquí.
</Callout>

## Para llevar

- `TestClient` + pytest en tu máquina; aquí, `httpx.AsyncClient` con `await`: la misma idea.
- Un test vale lo que detecta: mete bugs a propósito y mira si alguno falla.
- Comprueba código **y** cuerpo de la respuesta.
- Cada test con su base de datos limpia, sustituyendo `get_session` con `dependency_overrides` (y limpiándolo después).
- Si los tests fallan según el orden, busca estado compartido.
