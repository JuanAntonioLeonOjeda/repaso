Un modelo que solo vive en un notebook no le sirve a nadie. El último paso es guardarlo, cargarlo en otro proceso y darle imágenes nuevas **exactamente igual** que en el entrenamiento. Parece trivial, y es donde más modelos fallan en producción sin dar ningún error: el modelo devuelve una clase, solo que no la correcta.

## Guardar los pesos, no el objeto

```python
torch.save(model.state_dict(), "cnn_reg.pt")      # un dict {nombre_de_capa: tensor}
```

El `state_dict` es un diccionario con los tensores de cada capa: pesos, sesgos y también las estadísticas acumuladas de BatchNorm. Para cargarlo, creas el modelo con el mismo código y le pones los pesos:

```python
model = SmallCNN(dropout=0.3)
model.load_state_dict(torch.load("cnn_reg.pt", map_location="cpu"))
model.eval()
```

Nuestro checkpoint ocupa 1,25 MB: 308.394 parámetros en `float32` (4 bytes cada uno) más las estadísticas de BatchNorm.

## El mismo preprocesado, siempre

La red solo sabe ver imágenes de 32×32, en RGB, en CHW, en $[0, 1]$ y normalizadas con las estadísticas de CIFAR-10. En producción la imagen llega como un fichero JPEG de cualquier tamaño. La función que la prepara tiene que hacer **lo mismo** que `eval_tf`:

```python
from PIL import Image

preprocess = transforms.Compose([
    transforms.Resize((32, 32)),
    transforms.ToTensor(),
    transforms.Normalize(CIFAR_MEAN, CIFAR_STD),
])

@torch.no_grad()
def predict(image: Image.Image) -> list[tuple[str, float]]:
    x = preprocess(image.convert("RGB")).unsqueeze(0)   # (1, 3, 32, 32): un lote de una imagen
    probs = torch.softmax(model(x), dim=1)[0]
    top = probs.topk(3)
    return [(CLASSES[i], round(p.item(), 3)) for p, i in zip(top.values, top.indices)]
```

Con la primera imagen del test, un gato, la CNN regularizada devuelve `[('gato', 0.954), ('perro', 0.046), ('rana', 0.0)]`: la confusión gato-perro de la lección anterior asoma incluso cuando acierta.

Cuando el preprocesado de producción no coincide con el de entrenamiento se habla de *training-serving skew*. El caso clásico: alguien lee las imágenes con OpenCV, que las devuelve en **BGR**, no en RGB.

## Detrás de una API

Con `predict` ya tienes el núcleo de un servicio. El tutorial de FastAPI enseña a envolverlo en una API: cargar el modelo **una vez** al arrancar (lifespan), validar la entrada, predecir en lote y versionar el modelo.

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI, UploadFile

@asynccontextmanager
async def lifespan(app: FastAPI):
    model.load_state_dict(torch.load("cnn_reg.pt", map_location="cpu"))
    model.eval()
    yield

app = FastAPI(lifespan=lifespan)

@app.post("/predict")
def classify(file: UploadFile):        # def, no async def: la inferencia bloquea la CPU (UploadFile necesita python-multipart)
    image = Image.open(file.file)
    return {"top3": predict(image)}
```

<Callout kind="real" title="En el trabajo">
- **Exporta para servir sin Python o más rápido.** `torch.onnx.export` genera un modelo ONNX que corre en ONNX Runtime o TensorRT; `torch.export` es la puerta de entrada a ExecuTorch (móviles) y a la compilación anticipada. En los dos casos no hace falta tu código de entrenamiento. Comprueba siempre que el modelo exportado da las mismas salidas que el original con un lote de prueba.
- **Guarda con el modelo todo lo necesario para usarlo**: la versión del código, las clases en orden, el preprocesado (tamaño, media, std) y las métricas de validación. Un `.pt` suelto, sin saber qué clase es el índice 3, no vale para nada.
- **Monitoriza la entrada, no solo la salida.** Si la distribución de las imágenes cambia (otra cámara, otra luz), el accuracy cae sin aviso. Vigilar la media de los píxeles o la confianza media de las predicciones detecta muchos problemas antes de que los vea un usuario.
</Callout>

<Callout kind="idea" title="En Keras">
`model.save("modelo.keras")` guarda arquitectura y pesos juntos en un formato propio (no pickle), y `keras.models.load_model` lo recupera sin el código de la clase si usas capas estándar. PyTorch separa las dos cosas: el código define la arquitectura y el fichero solo trae los pesos.
</Callout>

## Para llevar

- Guarda `state_dict()`; carga con el mismo código, `load_state_dict` y `eval()`.
- El preprocesado de producción tiene que ser idéntico al de entrenamiento: mismo tamaño, mismo orden de canales, mismas estadísticas. Un único módulo para los dos.
- En inferencia, `model.eval()` y `torch.no_grad()`, las dos cosas.
- Para servirlo: el tutorial de FastAPI. Para servirlo rápido o fuera de Python: ONNX (`torch.onnx.export`) o ExecuTorch (`torch.export`).
